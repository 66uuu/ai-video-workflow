# 04 · 速度与一致性优化

> 解决两个真实问题：**出片太慢**、**视频里人脸和身材会变**。
> 数字全部来自本机实测（RTX 4060 Laptop 8GB / Wan2.2 TI2V-5B Q5_K_M / 草稿档 384×576 / 12 步 / euler）。
> 想自己复测：`python 09_工具脚本/bench.py`。

---

## 一、先把账算清：时间到底花在哪

同一档参数，只改帧数，实测三组：

| 帧数 | 耗时 |
|---|---|
| 13 帧 | 87.7 秒 |
| 25 帧 | 108.9 秒 |
| 49 帧 | 133.4 秒 |

线性拆解：

- **每帧成本** = (133.4 − 87.7) ÷ (49 − 13) ≈ **1.27 秒/帧**
- **固定开销** = 87.7 − 13 × 1.27 ≈ **71 秒/次**

**这 71 秒不是采样，是模型加载。** 边跑边看显存就能确认：

```
t= 5s   4635 MiB  89%   ← 上一条在收尾
t=13s   1467 MiB   0%   ← 模型已被卸掉，只剩桌面占用
t=40s   1467 MiB   0%   ← 一直空转，GPU 一点没动
t=45s   5307 MiB  14%   ← 模型这才进显存，开始算
```

中间这 27–36 秒，GPU 利用率 0%、CPU 只有约 1 核在忙、磁盘读取为 0
—— 是 GGUF 权重的反量化/装载，纯单线程 CPU 活。

**所以真正的结论是：慢的不是采样，是"每跑一条都要重新加载一次模型"。**
24 个镜头 × 71 秒 ≈ 28 分钟纯等待，这正好对上"一条完整视频 30–40 分钟"的体感。

## 一之二、最大的一个优化：一次性入队（已内置，不用你动手）

同样 3 条 13 帧，两种跑法实测对比：

| 跑法 | 第 1 条 | 第 2 条 | 第 3 条 | 合计 |
|---|---|---|---|---|
| 逐条 `submit → 等 → submit` | 88 s | 88 s | 88 s | **264 s** |
| **一次性全部入队** | 85 s | **24 s** | **27 s** | **136 s** |

原因：逐条跑时，两条之间的空闲期 ComfyUI 会把模型卸掉，下一条又从零加载。
一次性入队后，任务之间没有空闲期，模型常驻，**从第 2 条起只要 25 秒左右**。

折算到 24 镜：**约 35 分钟 → 约 11 分钟（快 3.2 倍）**。

已经内置好了：

- `batch_local.py` 的默认路径已改成「先全部入队，再依次收片」，
  跑法不变，速度自动变快。
- 通用层直接调 `comfy.run_many([wf1, wf2, wf3])`，返回每条的文件路径列表。

```python
import nr_bridge as nb
c = nb.Comfy()
wfs = [nb.build_i2v(img, p, 49, **nb.PROFILES["draft"]) for p in prompts]
c.run_many(wfs, r"<D盘>\产出", label=["S01", "S02", "S03"])
```

> 注意：这条优化对「一次跑多条」有效。如果你**只跑一条**，那 71 秒省不掉，
> 只能靠降帧数、降步数（见第二节）。

## 一之三、链路体检：先确认没有硬伤

本机基线：**13 帧约 88 秒**（含 71 秒加载）。如果明显超过，按顺序查：

| 检查 | 怎么查 | 正常值 | 不正常说明 |
|---|---|---|---|
| **1. 是不是在用 GPU** | ComfyUI 启动日志搜 `Device:` | `cuda:0` | 显示 `cpu` → 装的是 CPU 版 torch，必慢 10 倍以上 |
| **2. 是不是低显存模式** | 启动参数有没有 `--lowvram` / `--novram` | 无 | 有 → 模型反复换入换出，删掉这些参数 |
| **3. 帧数** | `--list` 看目标帧数 | 49–72 | 121 帧 = 572 秒，本身就翻倍 |
| **4. 分辨率** | 镜表的 model 块 | 512×768 | 768×1152 是 2.25 倍像素，时间也翻倍 |
| **5. 步数** | 同上 `steps` | 20–24 | 40 步以上收益很小，时间线性涨 |
| **6. 显存是否被别的软件占着** | `nvidia-smi` 看 used | 空闲 >5G | **AutoCAD、Edge 浏览器常占 3–4G**，直接导致模型留不住 |
| **7. 是否每次重载模型** | 见 `一之二` | 一批只加载一次 | 逐条跑就会每次重载 |
| **8. 一次实测** | `python 09_工具脚本/bench.py --profiles draft --frames 25` | 约 110 秒 | 明显超过 → 前 7 项里有问题 |

**先跑第 8 项。** 如果 25 帧要几分钟，别急着调参数，先把链路修好——参数优化救不了 CPU 回退。

## 二、四档参数（按用途选，不要一直用最高档）

记住这个公式：**单条耗时 ≈ 71 秒（加载） + 帧数 × 每帧成本**。
批量跑时那 71 秒一批只付一次，所以「批量第 2 条起」这一列才是你实际的等待。

| 档位 | 分辨率 | 步数 | 采样器 | 每帧成本 | 单条 49 帧 | 批量第 2 条起 | 用途 |
|---|---|---|---|---|---|---|---|
| **draft** | 384×576 | 12 | euler / simple | **1.27 s（实测）** | 133 s | **约 62 s** | 看动作对不对、构图对不对 |
| **fast** | 448×672 | 16 | uni_pc / beta | ≈2.3 s（估算） | ≈190 s | ≈113 s | 内部审片、批量试镜 |
| **std** | 512×768 | 20 | uni_pc / beta | ≈3.8 s（估算） | ≈260 s | ≈185 s | 正式出片 |
| **hq** | 512×768 | 28 | dpmpp_2m / karras | ≈5.3 s（估算） | ≈330 s | ≈258 s | 特写、脸部镜头 |

> `uni_pc + beta` 是本包推荐的性价比组合：20 步大致追平 euler 24 步的收敛，
> 比 `dpmpp_2m + karras` 快、比 `euler + simple` 稳。

**关键**：先用 draft 把整集跑一遍看节奏，再只对"过了的镜头"跑 std。
不要一上来就对全部镜头跑 std —— 又慢，而且一半要重做。

## 四、不改参数也能省的几件事

| 做法 | 实测效果 | 说明 |
|---|---|---|
| **一次入队多条** | **3.2 倍（24 镜 35→11 分钟）** | 已内置，见 `一之二`。这是唯一的大杠杆 |
| **关掉 AutoCAD / 浏览器** | 显存从 3.5G 空余回到 7G+ | 它们常占 3–4G，模型因此留不住，每条都要重装 |
| **关采样预览** | 约 3–8% | 启动加 `--preview-method none`（已写进 `启动_优化.bat`） |
| **先出完关键帧再统一出视频** | 避免来回重载模型 | 出图↔出视频交替会把两套模型反复换入换出 |
| **断点续跑** | 避免重复算 | 已存在的镜头自动跳过；只重做 `--only S16 --force` |

**别浪费时间的三件事（都实测过，无效）：**

- `--cache-ram` —— 本来就是默认模式，显式写也不会让模型常驻
- `--use-sage-attention` / `--use-flash-attention` / `--enable-triton-backend` ——
  本机这三个包都没装，加了会直接启动失败
- 换更小的量化（Q4）—— 省得不多，画质掉得明显

## 五、人脸 / 身材为什么会变

Wan2.2 TI2V-5B 是个 **5B 的小模型**，图生视频时它只"参考"首帧，并不"锁定"首帧。
于是：

| 现象 | 原因 |
|---|---|
| 越到后面越不像 | 帧数越多，误差累积越大（121 帧最明显） |
| 一动就变形 | 动作幅度大，模型要靠想象补中间帧 |
| 脸糊、五官漂 | 512×768 本身分辨率低，脸部只占几十像素 |
| 身材比例变 | 全身入画 + 大动作（走路、转身）最容易崩 |
| 换个镜头就换人 | 每个镜头独立生成，没有跨镜一致性约束 |

### 先量，再修 —— 不要靠眼睛一帧帧看

`09_工具脚本/drift_check.py` 把"像不像"变成数字。它逐帧和首帧做**位移对齐后的结构相似度（NCC）**，
所以测的是"变形"，不是"走动"：

```bat
ComfyUI\venv\Scripts\python.exe 09_工具脚本\drift_check.py video_i2v\*.mp4
```

判读：

| 末段 NCC | 结论 | 怎么办 |
|---|---|---|
| ≥ 0.85 | 一致性好 | 直接用 |
| 0.70 – 0.85 | 轻微漂移 | 短镜头还行，长镜头会看出来 |
| < 0.70 | 主体明显变形 | 重拍，或把帧数砍短 |

同时它还会报 `ΔRGB`（中心区域颜色偏移，抓"肤色变白/整片变灰"）和 `运动量`（抓"死片"）。
**先跑一遍，只有 FAIL 的镜头才值得花时间重做**，比全片逐帧看快得多。

> 说明：这不是人脸识别，它测的是"画面主体结构相对首帧变了多少"，
> 对人物、产品、建筑都适用。数值低就代表变了，具体变在哪仍需自己看一眼。

## 六、六条对策（按性价比排序）

> 动手之前先做一件事：用 `09_工具脚本/gen_char_assets.py` 把**角色资产**做出来
> （正脸 / 半身 / 三视图 / 表情，约 90 秒）。后面每条镜头都挂同一张参考图，
> 比每条单独描述长相稳得多。做法见 `01_命令手册.md` 的 2.3。

### ① 缩短单镜（最有效，且同时提速）

**单镜不超过 72 帧（3 秒）**，特写不超过 60 帧。
漂移随帧数累积，砍长度是收益最高的一刀。长镜头拆成 2–3 个短镜头剪辑，比硬生成 5 秒稳得多。

### ② 动作幅度压小（零成本）

- 只写一个动作，且是"小动作"：抬头、低头、贴紧手机、视线移动
- 不写"走过整个画面""转身""起身"这类全身位移
- 用"极缓慢地""极轻地"限速，结尾"停住"

### ③ 首帧质量决定上限（很关键）

- 脸要**清晰、正面或 3/4 侧、光线均匀**，不要大逆光、不要半张脸在阴影里
- 关键帧出图后，**先做一次面部修复/重绘**（face detailer 或局部 inpaint），再拿去 I2V
- 首帧糊，视频一定糊；首帧脸歪，视频一定歪

### ④ 构图避开全身（零成本）

- 用**中景 / 近景 / 特写**，少用全景
- 全身入画时，腿和手最容易变形
- 必须全身时，让人物**基本站定**，只做上半身动作

### ⑤ 角色 LoRA（最彻底，但要训练）

用 15–30 张同一角色的图训一个 LoRA，出关键帧时挂上。
这是唯一能真正"跨镜头锁脸"的办法。代价是要花时间训练，且 5B 视频模型挂 LoRA 需要额外适配。

### ⑥ 后期人脸修复（兜底）

出片后用 GFPGAN / CodeFormer 逐帧修脸。
注意：逐帧独立修会**闪烁**，要开 temporal 稳定选项，或者只修关键帧不修视频。

## 七、推荐工作流（把 35 分钟压到 10 分钟级）

```
第 1 轮：草稿全跑（一次性入队，自动生效）
  batch_local.py --profile draft
  → 24 镜约 11 分钟出全集草稿，只看"动作对不对、构图对不对"

第 2 轮：自动筛 + 人工筛
  drift_check.py video_i2v\*.mp4
  → NCC < 0.70 的直接列出来，不用自己一帧帧看
  再人工看一遍"动作对不对、有没有出画"

第 3 轮：标准档只跑通过的镜头
  batch_local.py --profile std --only S03,S07,S13 --force
  → 只有通过的镜头才吃 3 分钟

第 4 轮：特写单独精修
  batch_local.py --profile hq --only S05 --force
```

**核心思路：便宜的先跑，贵的只跑对的，筛片交给脚本。**

## 八、一页速查

| 你遇到的问题 | 直接这么做 |
|---|---|
| 太慢 | 先确认是「一次跑多条」——批量入队能快 3.2 倍 |
| 只跑一条也很慢 | 那 71 秒加载省不掉，改降帧数/步数：`--profile draft` |
| 想先看全片 | `--profile draft` 跑全集，24 镜约 11 分钟 |
| 脸越走越不像 | 先跑 `drift_check.py` 定量，再砍帧数到 ≤72；动作压小 |
| 一动就变形 | 换中近景，别全身大动作 |
| 每个镜头像不同人 | 首帧统一用同一张脸 + 同一 LoRA；关键帧先修脸 |
| 出片糊 | 草稿只用于审片，正式片必须回 512×768 |
| 重复算 | 断点续跑已内置，只 `--only X --force` 重做 |
| 跑一批要守着 | `--submit-only` 压完就关终端，回头 `--collect` 收 |
| 不知道哪档合适 | `bench.py` 实测一遍，看「折算 72 帧」那一列 |

## 九、一句话

**速度靠"一次入队 + 先草稿"；一致性靠"先量化 + 短镜头 + 小动作 + 好首帧"。**
这两件事其实是同一个方向：**别让模型猜太多。**
